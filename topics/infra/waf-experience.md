# WAF — 겪은 것과 다음에 할 것

파일 업로드가 있는 API 서버에서 업로드만 403 으로 막힌 일을 겪고 정리한 것.

---

## 1. 무슨 일이 있었나

담당자가 엑셀을 올리면 403 이 뜨고, 화면에는 `Failed to fetch` 만 나왔다.

애플리케이션 쪽 403 사유를 하나씩 배제했다. 담당 기관도 붙어 있었고, 계약 정보도
멀쩡했고, 외부 인증 서버도 정상 응답이었다. **전부 아니었다.**

결정적 단서는 둘이었다.

- 같은 계정·같은 가드를 지나는 **조회는 200** 인데 업로드만 막혔다.
- 애플리케이션 로그에 그 요청이 **한 줄도 없었다.** 서버까지 오지도 못했다.

curl 로 직접 쏘니 답이 나왔다.

```
403 ERROR / Request blocked.
Generated by cloudfront (CloudFront)
```

`Request blocked.` 는 WAF 가 막았을 때 나오는 문구다. 허용되지 않은 메서드였다면
`Bad request` 나 405 가 나왔을 것이다.

`Failed to fetch` 도 여기서 설명된다 — **우리 앱이 낸 403 이면 CORS 헤더가 붙으므로
프론트가 본문을 읽는다.** 못 읽었다는 건 앞단에서 끊겼다는 뜻이다.
이 한 가지만 알아도 다음엔 앞단부터 의심하게 된다.

## 2. WAF 가 뭔가

방화벽인데 **보는 층이 다르다.**

| 층 | 무엇을 보나 |
| --- | --- |
| 네트워크 방화벽 | 누가 어느 포트로 들어오는가 |
| **WAF** | 요청 **내용**이 수상한가 (URL · 헤더 · 본문) |
| 인증·인가 | 이 사람이 이걸 할 자격이 있는가 |
| 응용 | 값이 규칙에 맞는가 |

네트워크 방화벽이 "이 골목으로 온 사람만" 들여보내는 것이라면,
WAF 는 **가방 안을 뒤져서** 위험한 게 있나 보는 것이다.

**막는 것** — 알려진 공격 패턴(SQL 인젝션 · XSS · 경로 탐색), 스캐너, 악성 IP, 요청 속도.

**못 막는 것** — **누구인지 모른다.** 인증을 대신하지 못한다. 인증이 빠진 엔드포인트를
WAF 는 그냥 통과시킨다. 실제로 우리도 무인증 경로가 그대로 200 으로 통과했다.

그래서 WAF 는 **애플리케이션이 실수했을 때의 보험**이지 주방어선이 아니다.

## 3. 왜 막혔나

클라우드가 제공하는 **기본 룰셋은 브라우저가 폼을 쓰는 웹앱**을 전제로 만들어졌다.
사람이 입력창에 글자를 치고 서버가 HTML 을 그리는 구조다.

JSON 과 파일을 주고받는 API 서버에는 잘 안 맞는다. 걸러줄 게 별로 없고 오탐만 남는다.

```
SizeRestrictions_BODY     본문 크기 제한(흔히 8KB)
                          → 파일 업로드가 통째로 막힌다
CrossSiteScripting_BODY   본문에서 스크립트 패턴 탐색
                          → xlsx·zip 같은 바이너리를 오탐한다
GenericRFI_BODY           본문에서 원격참조 패턴 탐색
                          → 같은 이유로 오탐
```

**크기 제한이 특히 함정이다.** 작은 테스트 파일은 통과하고 실제 업무 파일에서 터진다.
실사용 명단은 수백 건~수천 건이라 파일이 수백 KB 가 된다. 8KB 는 애초에 파일 업로드를
상정한 값이 아니다.

### ★ 우리가 켠 게 아니었다

Web ACL 이름이 `CreatedByCloudFront-` 로 시작했다. **배포 생성 마법사의 기본값이
"보호 기능 활성화"** 라 자동으로 붙은 것이다.

계정에 같은 형태의 ACL 이 열여덟 개 있었고 대부분 로깅이 꺼져 있었다 — 아무도 안 보고
있다는 뜻이다. 사람이 검토해서 만든 건 하나뿐이었다(규칙 수도 다르고 로깅도 켜져 있었다).

그래서 이건 **누군가의 보안 결정을 뒤집는 문제가 아니라, 기본값을 우리 상황에 맞게
조정하는 문제**였다. 판단의 무게가 달라진다.

## 4. 어떻게 했나

무료 플랜이라 **룰 그룹 안의 개별 룰을 Count 로 내리는 게 막혀 있었다.**
선택지가 좁아 이렇게 갈렸다.

| | 무엇 | 남는 보호 |
| --- | --- | --- |
| ① | 문제되는 룰 그룹만 제거 | 나머지 그룹 |
| ② | **모니터 모드** | 없음. 대신 "막혔을 요청" 통계가 쌓인다 |
| ③ | 보호 전체 끄기 | 없음 |

**②를 골랐다.** ①은 UI 에서 막혀 있었고, ③보다 ②가 나은 이유는 나중에 제대로 붙일 때
**추측이 아니라 데이터로** 예외를 정할 수 있어서다. 되돌리기도 체크 하나다.

방어력은 ②와 ③이 같다. 그래도 ②를 고른 건 **자료가 남기 때문**이다.

끄기 전에 확인한 것 — **그 ACL 이 우리 것 하나에만 붙어 있는지.**
하나의 ACL 이 여러 리소스에 붙어 있으면 끄는 순간 다 풀린다.

## 5. 다음부터 — 순서를 뒤집지 않는다

이번 사고의 본질은 **관찰 없이 차단부터 켠 것**이다. 제대로 쓰는 순서는 반대다.

```
① 붙이되 차단하지 않는다      모니터 모드 · 로깅 켜기
② 실제 트래픽으로 관찰         2~4주. 정상 업무가 다 돌아본 뒤
③ 오탐 목록을 뽑는다           "막혔을 뻔한" 요청 중 정상인 것
④ 예외를 정의한다              경로 단위로 좁게
⑤ 그때 차단으로 전환           ★ 마지막이지 처음이 아니다
⑥ 전환 후에도 로그를 본다      관리형 룰셋은 제공자가 조용히 갱신한다
```

②를 건너뛰면 정상 업무가 첫 사용자에게서 터진다.

**관찰할 때 판단 기준**은 셋이다. 우리가 만든 요청인가, 정상 업무 흐름인가,
**앞으로 더 커질 것인가.** 세 번째가 핵심이다 — 지금 안 걸렸다고 안전한 게 아니라
실제 규모로 계산해 봐야 한다.

**예외는 좁게 잡는다.**

```
좋다   업로드 경로에서만 해당 룰을 Count
나쁘다 그 룰을 전역에서 Count
최악   룰 그룹을 통째로 제거
```

**자동 생성물은 쓰지 않는다.** 딸려오는 기본 보호는 켜기/끄기밖에 안 되고 손대도
덮어써진다. 위 ①~⑤ 절차를 밟을 수가 없다. **직접 정의한 ACL 을 붙이고, 그걸 코드로
관리한다.** 콘솔에서 체크박스로 관리하면 반년 뒤 아무도 왜 그런지 모른다.

## 6. 새로 설계할 때

### 위임의 선은 "신원"이다

WAF 가 잘하는 건 **신원을 몰라도 판단되는 것**이다. 공격 패턴, 요청 속도, 지역, 봇, IP 평판.
"이 사람이 이 조직 담당인가"는 WAF 가 알 수 없다.

그래서 **신원이 필요하면 애플리케이션, 필요 없으면 앞단**이다.

### 원칙 셋

**아래층이 없어도 위층이 버텨야 한다.** WAF 를 끄면 뚫리는 설계면, WAF 가 앱의 구멍을
가리고 있던 것이다. 우리가 껐을 때 크게 위험하지 않았던 건 인증·인가가 제자리에
있었기 때문이다. 그게 정상이다.

**싼 층에서 먼저 거른다.** 네트워크 < WAF < 앱 순으로 비싸다. 단 **확실할 때만**이다.
애매한 걸 앞에서 자르면 오탐이 된다.

**한 가지를 두 층에서 막지 않는다.** 같은 규칙이 두 군데 있으면 한쪽만 고치는 날이 온다.
다만 **층이 다르면 중복이 아니다** — 앞단이 출발지를 막고 앱이 신원을 막는 건 둘 다 필요하다.

### 착수 시 체크리스트

```
□ 이 경로에 신원이 필요한가        필요 없으면 앞단 후보
□ 파일·대용량을 받는가             ★ 받으면 앞단 크기 제한을 설계 단계에서 확인
□ 실사용 규모로 계산했는가          테스트 파일 크기로 판단하지 않는다
□ 공개 경로가 있는가               속도 제한을 어디서 걸지 정한다
□ 관리·문서 경로가 있는가          앞단에서 IP 제한
□ 기본 보호가 자동으로 붙었는가    ★ 리소스 만들 때마다 확인
□ 로깅이 켜져 있는가               이게 없으면 원인을 못 찾는다
□ WAF 를 꺼도 안전한가             아니라면 앱 쪽이 비어 있다는 뜻
```

★ 두 줄이 이번에 배운 것이다.

## 7. 증상으로 구분하기

WAF 가 막은 요청은 **애플리케이션 로그에 안 남는다.** 서버에 닿기 전에 끊기기 때문이다.
이게 가장 확실한 판별법이다.

| 증상 | 의심 |
| --- | --- |
| 서버 로그에 요청이 없다 | 앞단(WAF · LB · CDN)에서 차단 |
| 브라우저에 `Failed to fetch` 만 | 응답에 CORS 헤더가 없다 → 앱이 낸 에러가 아니다 |
| GET 은 되는데 POST 만 안 된다 | 메서드 제한 또는 본문 검사 룰 |
| 작은 파일은 되고 큰 파일만 | 본문 크기 제한 |
| 특정 파일 형식만 | 바이너리 오탐 |

차단 문구가 "blocked" 계열이면 WAF, "bad request" 나 405 면 메서드 제한 쪽이다.

## 8. 참고 — 다시 이런 일이 생기면

```bash
# 이 배포에 붙은 Web ACL
aws cloudfront get-distribution --id <배포ID> \
  --query 'Distribution.DistributionConfig.WebACLId' --output text

# 그 ACL 이 다른 배포에도 붙었는지 ★ 끄기 전에 반드시
aws cloudfront list-distributions \
  --query "DistributionList.Items[?WebACLId=='<ARN>'].{Id:Id,Alias:Aliases.Items[0]}" \
  --output table

# 차단된 요청과 룰 이름 (샘플은 3시간만 보관된다)
NOW=$(date +%s)
aws wafv2 get-sampled-requests --web-acl-arn '<ARN>' \
  --rule-metric-name ALL --scope CLOUDFRONT --region us-east-1 \
  --time-window StartTime=$((NOW-7200)),EndTime=$NOW --max-items 100 \
  --query 'SampledRequests[?Action==`BLOCK`].{Method:Request.Method,URI:Request.URI,Rule:RuleNameWithinRuleGroup}' \
  --output table
```

★ CloudFront 용 WAF 는 **`--scope CLOUDFRONT` · `--region us-east-1`** 이다.
다른 리전으로 보면 아무것도 안 나온다.
