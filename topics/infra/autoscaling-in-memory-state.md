# 오토스케일링 전에 풀어야 했던 것 — 메모리 상태와 크론

2026-09 · NestJS · NCP(공공존) · PostgreSQL · pm2

## 상황

- 서버 한 대에서 fork 모드 프로세스 1개로 돌던 NestJS API 서버에 오토스케일링을 붙이려고 했다.
- 처음에는 서버 이미지를 뜨고 Launch Configuration, Auto Scaling Group을 만들면 끝나는 인프라 작업이라고 생각했다.
- 막상 코드를 보니 ecosystem.config.js에 "cluster로 바꾸면 두 군데가 깨진다"는 주석이 있었다. 서버를 여러 대로 늘리는 것도 같은 문제였다.
  1. 크론이 서버마다 돈다.
  2. 파일 하나가 특정 서버 메모리에만 있다.
- 두 가지 모두 서버가 한 대일 때는 드러나지 않는다.

---

## 1. 크론 — 서버마다 돈다

### 상황

- `@nestjs/schedule`의 `@Cron` 워커가 세 개 있었다.
  - 매분: 변환
  - 10분마다: 멈춘 행 복구
  - 매일 새벽: 외부 전송
- 겹침 방지는 `isRunning` 플래그였다. 이건 프로세스 안에서만 유효해서, 서버가 두 대면 두 대가 같은 분에 같이 돈다.
- 변환 워커는 행을 `SKIP LOCKED`로 집어서 데이터는 지켜진다. 하지만 같은 사람을 동시에 집으면 외부 API를 두 번 부른다. 건당 과금이라 그대로 비용이 된다.
- 전송 워커는 미전송 행을 잠그지 않고 읽는다. 두 대가 돌면 같은 행을 두 번 보낸다.

### 고민한 방법

| 방법 | 장점 | 단점 |
|---|---|---|
| 워커 전용 서버 분리 (`WORKER_ENABLED` 같은 플래그로 크론을 한 대에서만 켬) | 구조가 단순하고, API 부하와 분리된다 | 서버가 한 대 더 필요하다. 그 서버가 죽으면 변환이 멈춘다 |
| **DB advisory lock** | 서버를 늘리지 않아도 된다. 한 대가 죽으면 다음 주기에 다른 서버가 이어받는다 | 잠금을 잡는 동안 커넥션을 하나 더 쓴다 |

### 왜 advisory lock으로 했나

- 공공존은 서버를 한 대 늘리는 데도 비용과 자원 신청이 따라온다.
- 워커 서버가 단일 장애점이 되는 것도 싫었다.
- PostgreSQL을 이미 쓰고 있어서 새로 들일 인프라가 없다.

### 구현 메모

```ts
const [{ locked }] = await queryRunner.query(
  "SELECT pg_try_advisory_lock(hashtextextended($1, 0)) AS locked",
  [lockName]
);
if (!locked) return false; // 다른 서버가 돌고 있다 — 이번 주기는 건너뛴다
try {
  await task();
} finally {
  await queryRunner.query("SELECT pg_advisory_unlock(hashtextextended($1, 0))", [lockName]);
}
```

- **세션 잠금을 썼다.** 트랜잭션 잠금(`pg_try_advisory_xact_lock`)은 작업 내내 트랜잭션을 열어 둬야 하고, `idle_in_transaction_session_timeout`이 걸려 있으면 중간에 끊긴다.
- **반드시 unlock 후 release 한다.** 잠금을 풀지 않고 커넥션을 풀에 돌려주면, 그 커넥션이 살아 있는 동안 잠금도 살아 있다. 그러면 어느 서버도 다시 그 작업을 못 돈다.
- **잠금 키는 문자열 해시로 만든다.** `hashtextextended`를 쓰면 숫자 키를 따로 관리하지 않아도 된다.
- **잠금은 DB 단위다.** dev·stage·prod가 DB 이름으로 나뉘어 있으면 서로의 잠금에 걸리지 않는다.
- **막는 건 "동시 실행"이다. "주기당 1회"가 아니다.** 앞 서버가 금방 끝내고 풀면 몇 ms 늦게 깬 서버가 한 번 더 돌 수 있다. 작업이 상태 기반(PENDING만 집는다, sentAt이 빈 것만 보낸다)이라 뒤따라 돈 쪽은 할 일이 없다. 멱등하지 않은 작업이면 이걸로는 부족하다.
- **건너뛸 때는 로그를 남기지 않는다.** 서버 N대면 매분 N-1줄이 쌓여서 봐야 할 로그가 묻힌다.
- **PgBouncer 트랜잭션 풀링을 앞에 두면 이 방식은 깨진다.**

## 2. 반려 파일 — 특정 서버 메모리에만 있다

### 상황

- 엑셀 명단을 올리면 1단계에서 검사만 한다. 문제가 있는 행이 있으면 원본 전체에 "반려 사유" 열을 붙인 엑셀을 만든다.
- 이 파일은 서버 메모리(`Map`)에 10분 보관하고, 응답에는 다운로드 토큰만 준다.
- **파일에 개인정보가 들어 있다.** 그래서 디스크·DB 어디에도 남기지 않기로 한 설계다. 서버가 죽으면 같이 사라지고, 담당자가 다시 올리면 된다.
- 서버가 여러 대가 되면 검사한 서버와 다운로드 요청을 받은 서버가 달라질 수 있다. 그러면 404가 난다. 매번이 아니라 가끔 나서 원인을 찾기 어려운 종류다.

### 보통 알려진 세 가지 방법

1. **스티키 세션:** 로드밸런서가 특정 클라이언트를 특정 서버에 고정한다. 쿠키 방식과 클라이언트 IP 방식이 있다.
2. **세션 클러스터링:** 서버끼리 세션을 복제한다.
3. **외부 저장소:** Redis나 DB에 둔다.

### 각각 왜 안 됐나

**3. 외부 저장소**
- 개인정보를 저장하지 않는 게 전제라서 제외했다.
- 앱에서 암호화한 뒤 TTL을 걸어 Redis에 두는 방법도 생각했다. 그래도 보관처가 하나 늘어나는 건 같다. 암호화, 보관 기간, 파기 절차가 전부 따라온다.

**2. 세션 클러스터링**
- Tomcat 같은 WAS에는 기본 기능으로 있지만 Node에는 없다. 직접 만들어야 한다.
- 오토스케일링과 잘 맞지 않는다. 서버가 뜰 때마다 기존 서버들이 새 서버 주소를 알아야 한다.
- 반려 파일이 모든 서버 메모리에 복제된다. 개인정보 사본이 서버 수만큼 늘어나서, 보관처를 늘리지 않는다는 설계와 정면으로 어긋난다.

**1. 스티키 세션** — 제일 싸 보였는데 조건이 붙었다.
- **IP 방식은 안 된다.** 로드밸런서 앞에 CloudFront가 있어서 LB가 보는 IP는 사용자 IP가 아니라 엣지 IP다. 요청마다 바뀔 수 있다.
- **쿠키 방식은 origin 문제가 있다.** 화면과 API가 같은 사이트의 다른 서브도메인이라 origin이 다르다. 브라우저 `fetch`는 기본값으로 다른 origin에 쿠키를 싣지도, 받은 쿠키를 저장하지도 않는다. 그래서 필요한 게 늘어난다.
  - 프런트: `credentials: "include"`, axios면 `withCredentials: true`
  - 서버 CORS: origin을 `*` 대신 명시하고 `credentials: true`. 둘은 한 세트다. origin이 `*`인 채로 프런트가 credentials를 켜면 브라우저가 응답을 막는다.
  - 로드밸런서 Target Group의 스티키 설정
  - 반영 순서: 서버를 먼저 올리고 프런트를 나중에 올려야 한다.
- 화면과 API가 **완전히 다른 사이트**였다면 더 나빴다. 스티키 쿠키가 제3자 쿠키가 되어 Safari에서는 아예 안 되고, Chrome도 `SameSite=None`이 붙어 있어야 한다. LB 쿠키의 속성은 우리가 정할 수 없다.
- 결국 "로드밸런서 옵션 하나 켜면 끝"이 아니라 프런트·서버·인프라 세 곳을 같이 바꿔야 해서 보류했다.

### 대안 1 — 서버 간 전달 (프런트·LB 변경 없음)

```
[검사]      브라우저 → LB → A   파일을 A 메모리에 보관
                               토큰에 A의 사설 IP를 넣고 서명
[다운로드]  브라우저 → LB → B   B에는 없음 → 토큰에서 A 주소를 읽음
                  B → A        내부망으로 직접 요청 (LB를 거치지 않음)
            브라우저 ← B        받은 파일을 그대로 전달
```

- 세션 클러스터링의 가벼운 변형이다.
  - 클러스터링: 모든 서버에 미리 복제한다. 그래서 서버 목록을 항상 알아야 한다.
  - 전달: 필요할 때 파일을 가진 서버 한 곳에서만 가져온다. 주소가 토큰에 있어서 서버 목록이 필요 없다.
- 파일은 여전히 원래 서버 메모리에만 있다.
- 서버가 한 대면 지금과 동작이 같다.
- 챙길 것
  - **내부 API 보호:** 서버끼리만 쓰는 API라서 공유 비밀값으로 서명한 요청만 받는다. 타임스탬프를 넣어 재사용도 막는다.
  - **토큰 서명:** 토큰 안의 서버 주소도 서명한다. 주소를 바꿔 엉뚱한 내부 주소를 부르게 하는 SSRF를 막기 위해서다.
  - **권한 전달:** 요청자 권한(기관 코드)도 서명해서 넘기고, 원래 서버가 지금처럼 소유를 대조한다.
  - **스케일인:** 원래 서버가 내려가면 파일도 사라진다. 원래 설계(재시작 시 소실)와 같은 수준이다.
  - **보안 그룹:** 서버끼리 앱 포트로 통신이 열려 있어야 한다.
- 같은 원리의 공식 사례로 Kafka Streams의 Interactive Queries가 있다. 상태를 가진 인스턴스를 찾아 RPC로 대신 조회해 온다.

### 대안 2 — 서버를 상태 없이 만들기 (프런트 변경 필요)

- **검사 응답에 반려 파일을 바로 담는다.** 보관소, 다운로드 API, 토큰이 전부 사라진다. 원래 이 방식을 피한 이유는 base64로 1.33배가 되는 응답 크기였는데, 명단 크기(수 MB)를 생각하면 감당할 만하다.
- **서버는 `{ rowNo, reason }` 목록만 주고, 반려 파일은 브라우저에서 만든다.** 브라우저가 방금 올린 원본을 이미 갖고 있으니 열 하나만 붙이면 된다. 개인정보가 응답으로 다시 나가지도 않아서 가장 깔끔하다.

### 판단

- 프런트를 건드리지 않는다면 **서버 간 전달**이 최선이다.
- 화면이 아직 개발 중이라 프런트를 바꾸는 비용이 가장 낮은 시점이다. 응답 형식을 조정할 수 있다면 **상태 없는 방식**이 구조가 더 단순하다.

## 배운 것

- **오토스케일링은 인프라 작업이 아니라 "서버가 상태를 갖고 있는가"를 묻는 작업이다.** 콘솔에서 ASG를 만드는 것보다 코드에서 메모리 상태, 크론, 로컬 파일을 찾는 게 먼저다.
- **`isRunning` 같은 프로세스 로컬 플래그는 서버가 늘어나는 순간 의미가 없어진다.** 분산 잠금이 필요하면 이미 쓰는 DB의 advisory lock이 가장 싸다.
- **스티키 세션은 LB 옵션이지만, 쿠키를 주고받는 건 브라우저다.** 앞단 구성(CDN 유무, 화면과 API의 origin 관계)에 따라 프런트와 CORS까지 바꿔야 한다.
- **개인정보를 저장하지 않는다는 제약은 선택지를 크게 줄인다.** 이 경우에는 "저장하지 않고 옮기기"(서버 간 전달)나 "애초에 들고 있지 않기"(상태 없는 설계)로 풀어야 한다.
- **오토스케일링 이미지를 뜨기 전에 확인할 것**
  - pm2 자동 시작(`pm2 startup`, `pm2 save`)
  - dev·stage 프로세스가 같이 뜨지 않는지
  - 배포가 서버에서 빌드하는 방식이면 산출물 방식으로 바꿀 것
