GoF 디자인 패턴 정리 (정보처리기사 대비)
핵심 3줄
• GoF 패턴 = *23개*, 분류는 *생성 5 / 구조 7 / 행위 11*
• 정처기는 "패턴 설명 → 이름 맞추기"와 "이 패턴이 어느 분류인가" 두 가지가 전부
• *아키텍처 패턴(레이어·MVC·파이프필터 등)과 헷갈리게 하는 문제*가 최대 함정
1. GoF 디자인 패턴이란?
GoF는 *Gang of Four*의 약자로, 다음 4명의 저자가 정리한 객체지향 디자인 패턴을 의미한다.
• Erich Gamma
• Richard Helm
• Ralph Johnson
• John Vlissides
GoF 디자인 패턴은 총 *23개*이며, 목적에 따라 다음 3가지로 분류된다.
   분류 목적 패턴 수     생성 패턴 객체를 어떻게 생성할 것인가 5개   구조 패턴 객체와 클래스를 어떻게 조합할 것인가 7개   행위 패턴 객체들이 어떻게 협력하고 책임을 나눌 것인가 11개
2. 시험 출제 포인트
필기 (1과목 소프트웨어 설계)
• 분류별 패턴 개수 / 특정 패턴이 어느 분류인지
• 패턴 설명과 이름 매칭 (보기 4개 중 고르기)
• GoF 패턴이 *아닌 것* 고르기 → 아키텍처 패턴을 섞어서 출제
실기 (단답형)
• 서술된 설명을 읽고 *패턴명을 직접 써야 함* → 눈으로만 보면 안 되고 철자까지 외워야 함
• 답안은 한글·영문 모두 인정되는 경우가 많지만, *한글 용어로 문제가 나옴* (옵서버, 퍼사드, 플라이웨이트, 책임 연쇄, 감시자, 방문자, 중재자, 반복자)
3. 분류 암기법
&gt;    분류 두문자 풀이     생성 (5) *추빌팩프싱* 추상팩토리 · 빌더 · 팩토리메소드 · 프로토타입 · 싱글톤   구조 (7) *어브컴데퍼플프* 어댑터 · 브리지 · 컴포지트 · 데코레이터 · 퍼사드 · 플라이웨이트 · 프록시   행위 (11) 나머지 전부 책임연쇄 · 커맨드 · 인터프리터 · 반복자 · 중재자 · 메멘토 · 옵서버 · 상태 · 전략 · 템플릿메소드 · 방문자   구조 패턴 7개는 *전부 "객체를 어떻게 끼워 맞추나"* 라는 목적을 공유한다. *생성 5개만 확실히 외우면*, 구조 7개는 소거법으로 잡히고 나머지는 자동으로 행위.
4. 전체 패턴 한 줄 요약
생성 패턴 (5)
   패턴 한 줄 요약     Abstract Factory 관련된 객체 묶음을 생성한다.   Builder 복잡한 객체를 단계적으로 생성한다.   Factory Method 객체 생성을 하위 클래스에 맡긴다.   Prototype 기존 객체를 복제한다.   Singleton 객체를 하나만 생성한다.   구조 패턴 (7)
   패턴 한 줄 요약     Adapter 서로 다른 인터페이스를 연결한다.   Bridge 추상과 구현을 분리한다.   Composite 부분과 전체를 동일하게 다룬다.   Decorator 객체를 감싸 기능을 추가한다.   Facade 복잡한 시스템을 단순하게 제공한다.   Flyweight 객체를 공유해 메모리를 절약한다.   Proxy 대리 객체로 접근을 제어한다.   행위 패턴 (11)
   패턴 한 줄 요약     Chain of Responsibility 요청 처리 책임을 다음 객체로 넘긴다.   Command 요청을 객체로 만든다.   Interpreter 문법을 정의하고 해석한다.   Iterator 컬렉션을 순차적으로 탐색한다.   Mediator 객체 간 통신을 중재한다.   Memento 객체 상태를 저장하고 복원한다.   Observer 상태 변화를 구독자에게 알린다.   State 상태에 따라 행동이 달라진다.   Strategy 알고리즘을 교체한다.   Template Method 처리 순서는 고정하고 일부 단계만 변경한다.   Visitor 객체 구조 변경 없이 기능을 추가한다.
5. 실기 대비 — 설명 → 패턴명
시험 지문은 대체로 아래 표현으로 나온다. *굵게 표시된 표현이 키워드*다.
생성 패턴
   지문 키워드 답     구체적인 클래스에 의존하지 않고 *서로 관련되거나 의존적인 객체들의 조합*을 생성 Abstract Factory   *복잡한 객체*를 생성 과정과 표현 방법을 분리해 *동일한 생성 절차로 서로 다른 표현* Builder   객체 생성을 *서브 클래스에서 처리*하도록 분리, 상위 클래스는 인터페이스만 정의 Factory Method   *원본을 복사*하여 새 객체를 생성 Prototype   클래스 내 *인스턴스가 하나뿐*임을 보장하고 어디서든 참조 Singleton   구조 패턴
   지문 키워드 답     *호환성 없는 인터페이스*로 인해 함께 사용할 수 없는 클래스를 연결 Adapter   *기능과 구현을 두 개의 별도 클래스로 구현*, 독립적으로 확장 Bridge   *전체-부분 관계*를 표현, 단일 객체와 복합 객체를 *동일하게* 취급 Composite   객체 간 결합을 통해 *동적으로 기능을 추가* Decorator   복잡한 서브 시스템에 대한 *통합된 인터페이스(단순한 창구)* 제공 Facade   인스턴스를 *공유*하여 메모리 절약 Flyweight   접근이 어려운 객체와 연결하는 *대리자*, 실제 객체의 *접근 제어* Proxy   행위 패턴
   지문 키워드 답     요청을 처리할 수 있는 객체가 *연결(체인)* 되어 처리하지 못하면 *다음 객체로 넘김* Chain of Responsibility   요청을 *객체의 형태로 캡슐화*하여 재이용·취소 가능 Command   언어에 따라 *문법 표현을 정의* Interpreter   컬렉션 구현 방법을 노출하지 않고 *순차적으로 접근* Iterator   객체 간 *직접 통신하지 않고 중개자를 통해* 통신, 결합도 감소 Mediator   특정 시점의 *객체 내부 상태를 저장했다가 복원* (Ctrl+Z) Memento   한 객체의 상태가 변하면 *의존하는 다른 객체들에게 통보* Observer   객체의 *상태에 따라 동일한 동작이 다르게* 처리 State   *알고리즘군을 캡슐화*하여 클라이언트가 독립적으로 교체 Strategy   상위에서 *골격(처리 흐름)을 정의*하고 하위에서 세부 처리 구체화 Template Method   처리 기능을 *분리하여 별도 클래스로* 구성, 구조 변경 없이 기능 추가 Visitor
6. 자주 헷갈리는 패턴 비교
Adapter vs Decorator vs Proxy vs Facade
모두 구조 패턴이지만 목적이 다르다.
   패턴 목적 핵심 질문     Adapter 인터페이스 변환 기존 객체의 인터페이스가 맞지 않는가?   Decorator 기능 추가 기존 객체에 기능을 동적으로 추가할 것인가?   Proxy 접근 제어 실제 객체에 대한 접근을 통제할 것인가?   Facade 사용 단순화 복잡한 시스템을 간단하게 보여줄 것인가?   Observer vs Mediator
   패턴 특징     Observer 한 객체의 상태 변화를 여러 구독자에게 알림   Mediator 여러 객체의 통신을 하나의 중재자가 관리   Strategy vs State
구조가 비슷하게 보일 수 있지만 목적이 다르다.
   패턴 기준     Strategy 사용자가 원하는 알고리즘을 선택   State 객체의 내부 상태에 따라 행동이 변경   Factory Method vs Abstract Factory
   패턴 특징     Factory Method 하나의 객체 생성을 하위 클래스에 위임   Abstract Factory 서로 관련된 여러 객체를 제품군으로 생성   Composite vs Decorator
   패턴 특징     Composite 객체를 트리 구조로 조합   Decorator 객체를 감싸서 기능 추가
7. 함정 포인트
1) 아키텍처 패턴 ≠ GoF 디자인 패턴 (출제 1순위)
&gt;    아키텍처 패턴 디자인 패턴(GoF)     레이어(계층화), 클라이언트-서버, 파이프-필터, *MVC(모델-뷰-컨트롤러)*, 브로커, 마스터-슬레이브, 피어투피어 위 23개   *MVC는 GoF 23개에 없다.* "다음 중 GoF 디자인 패턴이 아닌 것은?" → MVC / 파이프-필터 / 레이어가 답으로 자주 나옴.
2) 숫자 함정
"생성 6개", "구조 5개", "총 24개" 같은 식으로 숫자를 바꿔 낸다. → *5 / 7 / 11 = 23* 고정.
3) 표기 흔들림
Facade는 교재에 따라 *퍼사드 / 퍼싸드 / 파사드*, Observer는 *옵서버 / 옵저버 / 감시자*로 나온다. 실기에서는 *영문으로 쓰는 게 가장 안전*하다.
4) Bridge vs Adapter
• *Adapter*: 이미 만들어진 두 개를 나중에 붙임 (사후 대응)
• *Bridge*: 설계 단계부터 기능과 구현을 갈라놓음 (사전 설계)
5) Proxy vs Decorator
• *Proxy*: 접근 제어가 목적, 기능은 그대로
• *Decorator*: 기능 추가가 목적, 계속 겹쳐 쌀 수 있음
한 줄 정리
&gt; GoF 23개 = 생성 5(추빌팩프싱) + 구조 7(어브컴데퍼플프) + 행위 11. *MVC·레이어·파이프필터는 아키텍처 패턴이라 GoF가 아니다*는 것만 놓치지 않으면 필기는 잡히고, 실기는 "지문 키워드 → 패턴명" 표를 반대 방향으로 외우면 된다.
관련 문서
• 소프트웨어 아키텍처 패턴 (레이어, 클라이언트-서버, 파이프-필터, MVC, 브로커, 마스터-슬레이브, 피어투피어)
• 객체지향 설계 원칙 SOLID (SRP, OCP, LSP, ISP, DIP)
• 응집도와 결합도
• UML 다이어그램 (클래스, 시퀀스, 유스케이스)
