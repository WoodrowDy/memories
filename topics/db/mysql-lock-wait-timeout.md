# Lock wait timeout, 행 락이 아니었다

관리자 페이지의 엑셀 일괄 업로드 API가 세 번 연속으로 터졌다. 에러는 이거였다.

```
ERROR 1205: Lock wait timeout exceeded; try restarting transaction
```

"Lock"이라는 단어를 보면 누구나 같은 그림을 떠올린다. 누가 같은 행을 잡고 커밋을 안 했겠지. 나도 그랬고, 그래서 이틀을 엉뚱한 데서 헤맸다. 결론부터 쓰면 행 락이 아니라 메타데이터 락이었고, 범인은 코드 한 줄이었다.

## 증상

같은 파일로 5분 간격으로 재시도했고, 네 번째에 성공했다.

| 회차 | 소요 | 결과 |
|---|---|---|
| 1 | 100.2초 | 실패 |
| 2 | 82.8초 | 실패 |
| 3 | 73.7초 | 실패 |
| 4 | **0.3초** | 성공 |

4회차가 0.3초라는 게 이상했다. 데이터도 조건도 같은데 앞의 세 번은 70~100초를 쓰고 죽었다. 작업량 자체가 무거워서 생긴 문제는 아니라는 뜻이다.

## 1단계 — 애플리케이션 로그

행 락이라면 같은 행을 쥔 다른 쓰기가 반드시 있어야 한다. 그 시각대의 로그를 전부 훑었다.

**쓰기 요청이 한 건도 없었다.** 1회차도, 3회차도.

여기서 막혔다. 가해자가 없는데 74초를 기다렸다는 게 말이 안 됐다. 로그는 INFO 레벨이라 쿼리도 커밋 시점도 남지 않고, 배치는 HTTP 요청 로그로 잡히지도 않는다. 더 팔 게 없었다.

## 2단계 — 코드

스택 트레이스가 가리키는 줄을 열어봤더니 이랬다.

```ts
} catch (e) {
  await this.historyService.rollback(...);
  throw new HttpException(e, HttpStatus.INTERNAL_SERVER_ERROR);   // ← 스택이 가리킨 줄
}
```

catch에서 다시 던지는 자리였다. 어느 문장이 대기했는지는 알려주지 않는다. 스택만 보고 "여기가 문제"라고 했으면 그대로 헛다리였다.

대신 두 가지를 알아냈다. 이 메서드에는 트랜잭션 래퍼가 없다. 문장 단위 오토커밋이니 대기는 **문장 하나**에서 났다는 뜻이다. 그리고 실패하면 catch에서 롤백이 도는데 이게 수십 초짜리다. 즉 응답 시간은 이렇게 쪼개진다.

```
응답 시간 = 락 대기 + 롤백
```

70~100초를 통째로 대기로 보면 안 됐던 것이다.

## 3단계 — 전제를 세우고 DB로

어느 문장이 대기했는지 알아야 하는데 로그에는 없다. 그래서 전제를 하나 세웠다.

> 락에 걸려 죽었다면, 그 문장은 대기한 시간만큼 실행된 것으로 기록된다.

즉 어딘가에 비정상적으로 오래 걸린 문장이 남아 있어야 한다.

락 대기 현황을 보는 뷰(`sys.innodb_lock_waits`)는 **지금 이 순간 대기 중인 것만** 보여준다. 이미 끝난 사건에는 쓸 수 없다. 대신 서버 기동 이후 누적되는 문장별 통계를 봤다. 여기에는 문장마다 최대 실행시간이 남는다.

```sql
SELECT LEFT(DIGEST_TEXT, 200) AS stmt, COUNT_STAR, SUM_ERRORS,
       MAX_TIMER_WAIT/1e12 AS max_sec,
       AVG_TIMER_WAIT/1e12 AS avg_sec,
       FIRST_SEEN, LAST_SEEN
FROM performance_schema.events_statements_summary_by_digest
WHERE MAX_TIMER_WAIT/1e12 > 10
ORDER BY MAX_TIMER_WAIT DESC
LIMIT 50;
```

여기서 걸렸다.

```
TRUNCATE TABLE <스크래치 테이블>
  실행 3,201회 / 에러 3회 / max 61.0초 / avg 0.078초
```

평소 0.078초짜리가 최대 61초. 느린 게 아니라 뭔가에 걸려 죽은 모양이다.

## 61초라는 숫자

61초를 보고 목록을 다시 봤더니, 서로 아무 관계 없는 문장들의 최대 실행시간이 61~62초에 몰려 있었다.

```
ALTER TABLE ...      61.0017
TRUNCATE TABLE ...   61.0004
ALTER TABLE ...      61.0163
CREATE INDEX ...     61.1876
```

`ALTER` 와 `CREATE INDEX` 는 **행 락을 기다릴 수가 없는 문장이다.** DDL이니까. 이것들이 60초에서 잘렸다는 건, 이 서버에서 60초에 자르고 있는 게 행 락 타임아웃이 아니라는 뜻이다.

```
innodb_lock_wait_timeout   → 행 락용         (기본 50초)
lock_wait_timeout          → 메타데이터 락용
```

**두 타임아웃은 변수가 다른데 에러 번호와 메시지가 완전히 같다.** 1205, "Lock wait timeout exceeded". 그래서 구분이 안 된다. 힌트는 처음부터 숫자에 있었다. 50초가 아니라 60초였다.

에러가 난 시각을 확인해보니 계산도 맞아떨어졌다.

```
요청 시작 → 1205 발생 = 61초
성공 케이스 전체 소요  = 0.3초
```

작업 자체는 1초도 안 걸린다. 61초 중 60초는 순수 대기였다. 나머지 롤백 시간이 회차마다 달라서 70~100초로 흩어진 것이다.

## 메타데이터 락이 뭐냐

여기서 개념을 정리하고 가야 했다.

MySQL에는 성격이 다른 락이 두 층 있다. 하나는 익숙한 **행 락**으로, 데이터 내용물을 지킨다. 다른 하나가 **메타데이터 락(MDL)** 인데 이건 테이블의 구조를 지킨다.

왜 필요하냐면, 누가 `SELECT * FROM users` 를 실행하는 도중에 다른 세션이 컬럼을 지워버리면 안 되기 때문이다. 그래서 **어떤 문장이든 테이블을 건드리는 순간 메타데이터 공유 락이 자동으로 걸린다.** 코드에 쓴 적이 없어도 걸린다.

종류는 둘이다. 공유 락은 여러 세션이 동시에 가질 수 있고 서로 막지 않는다. 배타 락은 한 세션만 가질 수 있고, 공유 락이 하나라도 남아 있으면 못 들어간다.

```
DML (SELECT, INSERT, UPDATE, DELETE)  → 내용물 작업 → 메타데이터 공유 락
DDL (CREATE, ALTER, DROP, TRUNCATE)   → 구조 작업   → 메타데이터 배타 락
```

평소 수백 개 쿼리가 동시에 돌아도 멀쩡한 건 전부 공유 락이라 서로 안 막기 때문이다. 배타 락이 하나 끼어드는 순간 달라진다.

## TRUNCATE는 DELETE의 빠른 버전이 아니다

이게 핵심이었다.

```
DELETE   → 행을 하나씩 지움           → DML → 공유 락
TRUNCATE → 테이블을 버리고 새로 만듦  → DDL → 배타 락
```

결과는 같아 보이지만 동작이 다르다. TRUNCATE가 빠른 이유는 행을 지우지 않고 테이블을 통째로 갈아끼우기 때문이고, 그 대가가 배타 락이다.

그리고 문제의 코드는 이랬다.

```ts
await this.someRepository.clear();
```

TypeORM의 `clear()` 는 `TRUNCATE` 를 발행한다. 문서에는 "테이블의 모든 데이터를 지운다"라고만 써 있어서 DDL이라는 게 드러나지 않는다. 쓰는 사람 입장에서는 그냥 "비우기"다.

## 트랜잭션이 끼어드는 지점

규칙이 하나 있다.

> 메타데이터 락은 문장이 끝날 때가 아니라 **트랜잭션이 끝날 때** 풀린다.

오토커밋이면 문장 하나가 곧 트랜잭션이라 바로 풀린다. `BEGIN` 으로 열어두면 다르다.

```sql
BEGIN;
SELECT * FROM t LIMIT 1;   -- 공유 락 획득
-- 커밋하지 않고 방치
-- 쿼리를 더 날리지 않아도 공유 락은 계속 보유 중
```

그래서 이런 문장이 성립한다.

> **읽기만 하는 세션이 TRUNCATE를 막는다.**

행 락 세계에서는 성립하지 않는 말이다. InnoDB는 MVCC라 SELECT가 UPDATE를 막지 않는다. 메타데이터 락 층에서는 SELECT도 구조 변경을 막는다.

DB 클라이언트를 오토커밋 꺼놓고 쓰다가 자리를 비우면 정확히 이 상태가 된다. 조회 한 번 하고 커피 마시러 간 세션이, 다른 서버의 배치를 60초 세우고 죽인다.

전체를 그림으로 그리면 이렇다.

```
[누군가]  BEGIN; SELECT ...      → 공유 락 획득, 커밋 안 함
                                     ↓ 계속 보유
[배치]    TRUNCATE TABLE ...     → 배타 락 필요
                                     ↓ 앞 세션이 놓지 않음
                                    60초 대기 → ERROR 1205
```

덤으로, 대기 중인 배타 락은 **그 뒤에 오는 SELECT까지 막는다.** 대기열이 순서대로 처리되기 때문이다. 하나가 막히면 그 테이블 전체가 줄줄이 선다.

## 왜 하필 이 코드였나

문제의 테이블은 대량 UPDATE를 JOIN으로 처리하려고 쓰는 스크래치 테이블이었다. 값을 밀어넣고, JOIN으로 갱신하고, 비운다. 그런데 **요청을 구분하는 컬럼이 없었다.** 전역 공유 테이블이었던 것이다.

누구 것인지 구분이 안 되니 "전부 비운다"는 연산이 필요했고, 전부를 비우려다 보니 가장 센 수단을 쓰게 됐다. 상시 실행 경로 한복판에 DDL이 박혀 있던 셈이다.

평소에는 0.07초에 지나가니까 3,200번을 무사히 넘겼다. 확률이 낮았을 뿐 구조는 처음부터 그랬다.

## 고치는 방향

**비우는 행위를 DDL에서 DML로 내린다.** "테이블을 비운다"는 요구 자체에는 구조를 바꿀 이유가 없다. `DELETE` 로 내리면 공유 락만 쓰게 되고, 배타 락을 기다릴 일이 사라진다.

덤이 하나 더 있다. TRUNCATE는 DDL이라 **트랜잭션 한가운데에서 암묵적 커밋을 일으킨다.** 롤백도 안 된다. 지금은 트랜잭션 래퍼가 없어서 드러나지 않지만, 이 장애를 보고 "일괄 처리를 트랜잭션으로 묶자"고 고치는 순간 롤백이 절반만 되는 상태가 된다. 가장 자연스러운 다음 수정이 오히려 함정이다.

**다만 비우는 방법만 바꾸면 설계는 그대로다.** 근본은 임시 데이터에 소유자가 없다는 것이다. 임시 행에 요청 단위 소유권을 주면 "전부 비운다"가 "내 것만 지운다"로 바뀐다. 락 문제와 동시성 문제가 같은 수정 하나로 사라진다.

선택지는 몇 가지가 있다.

| 방식 | 얻는 것 | 감수할 것 |
|---|---|---|
| 요청 스코프 컬럼 + `DELETE` | 변경 범위가 작고 기존 구조 유지 | 공유 스크래치 테이블은 그대로 남음 |
| 세션 전용 임시 테이블 | 공유 자체가 사라져 경합 원천 차단 | 커넥션 풀과 수명 관리를 직접 다뤄야 함 |
| 임시 테이블 제거 — upsert | 왕복 1회, 중간 상태 없음 | 대상 키가 항상 확정돼 있어야 함 |
| 임시 테이블 제거 — 구조화 파라미터 JOIN | SQL 길이가 데이터량과 무관 | DB 버전 의존 |

어느 쪽을 택하든 같이 챙겨야 할 게 있다. **실패 경로에서도 정리되어야 한다.** 정리 코드가 성공 경로에만 있으면 예외가 났을 때 쓰레기가 남는다. 지금까지는 다음 요청의 TRUNCATE가 전부 밀어버려서 이 결함이 가려져 있었다. 비우는 범위를 좁히는 순간 드러난다.

## 재현해보기

개념은 세션 두 개면 눈으로 확인된다.

```sql
-- 세션 A
BEGIN;
SELECT * FROM t LIMIT 1;
-- 커밋하지 말고 그대로 둔다

-- 세션 B
TRUNCATE TABLE t;
-- 멈춰 있다가 ERROR 1205
```

멈춰 있는 동안 다른 세션에서 대기 상태를 볼 수 있다.

```sql
SELECT OBJECT_SCHEMA, OBJECT_NAME, LOCK_TYPE, LOCK_STATUS, OWNER_THREAD_ID
FROM performance_schema.metadata_locks
WHERE OBJECT_NAME = 't';
```

세션 A가 `SHARED_READ` / GRANTED, 세션 B가 `EXCLUSIVE` / PENDING 으로 뜬다.

MySQL 8은 MDL 계측이 기본으로 꺼져 있어서 테이블이 비어 보일 수 있다. 그럴 때는 먼저 켜야 한다.

```sql
UPDATE performance_schema.setup_instruments SET ENABLED = 'YES'
WHERE NAME = 'wait/lock/metadata/sql/mdl';
```

같은 방식으로 `DELETE` 는 막히지 않는다는 것도 확인된다. 세션 A를 열어둔 채 `DELETE` 를 실행하면 그대로 통과한다. 수정안까지 한 번에 증명되는 셈이다.

## 남은 것

- **상시 실행 경로에 DDL을 두지 않는다.** 하루에도 수십 번 도는 코드에 구조 변경이 섞여 있으면, 평소엔 빠르게 지나가다 겹치는 순간 전체가 선다
- **ORM이 감춘 SQL을 한 번은 확인한다.** `clear()` 처럼 무해해 보이는 편의 메서드가 DDL을 발행할 수 있다
- **공유 자원에는 소유자를 준다.** 소유자가 없으면 정리 연산이 항상 "전부"가 되고, 전부를 건드리는 연산은 가장 센 락을 요구한다
- **에러 메시지를 끝까지 믿지 않는다.** 1205는 두 가지 완전히 다른 상황에서 똑같은 문장으로 나온다. 구분은 숫자가 해줬다

그리고 하나 더. 이번에 DB 내부까지 내려간 이유는 애플리케이션이 단계별 소요 시간을 남기지 않았기 때문이다. 어느 단계에서 몇 초가 걸렸는지만 로그에 있었어도 5분이면 끝났을 일이다. 관측 가능성은 장애가 났을 때 비로소 가격표가 붙는다.
