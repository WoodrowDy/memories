# 위키 어시스턴트

> 슬랙에서 이 위키에 말을 걸면, 직접 뒤져서 답하고 나중엔 대신 정리까지 하는 봇.
> 코드는 [WoodrowDy/memories-wiki-bot](https://github.com/WoodrowDy/memories-wiki-bot).

---

## 지금 상태

| 단계 | 내용 | 상태 |
|---|---|---|
| 1단계 | 키워드 검색 — 멘션하면 노트를 찾아 경로·요약을 답한다 | ✅ 완료 |
| 2단계 | 자연어 브레인 — 모델이 툴을 골라 목록·본문을 읽고 답한다 | ✅ 완료 (2026-07-27 배포) |
| 3단계 | 쓰기 — 붙여넣은 글을 규칙대로 정리해 PR로 올린다 | 다음 |
| 이후 | 검색 품질, MCP 분리 | 미착수 |

## 왜 만드나

위키의 진짜 비용은 쓰는 게 아니라 **꺼내 쓰는 것**이다. 노트가 서른 개를 넘어가면
"그거 어디다 적었더라"가 검색보다 느려지고, 그 순간부터 위키는 무덤이 된다.

그래서 목표는 두 개다.

1. **찾기를 없앤다** — 폴더를 헤매는 대신 슬랙에서 물어본다 (1·2단계)
2. **정리 비용을 낮춘다** — 초안을 던지면 규칙에 맞게 다듬어 올린다 (3단계)

두 번째가 진짜 목표다. 오늘 [gRPC 노트](../topics/cs/grpc.md)를 정리하면서 든 손이
경로 정하기 → 줄바꿈 붙이기 → 코드블록 걷어내기 → 섹션 재배치 → 프론트매터 채우기 →
MOC·daily 연결이었는데, 이 일곱 단계가 전부 규칙 기반이라 자동화가 된다.

## 구조

```
Slack 멘션
   │
   ▼
API Gateway
   │
   ▼
gateway 람다      서명 검증 → SQS에 넣고 즉시 200
   │
   ▼ SQS
   │
worker 람다       Claude 툴 콜링 루프
   │                 ├ search_wiki   키워드로 찾기
   │                 ├ list_notes    목록 훑기
   │                 ├ read_note     본문 읽기
   │                 └ wiki_status   전체 통계
   ▼
스레드에 답글
```

**함수가 둘로 갈린 이유가 이 프로젝트의 핵심 제약이다.** 슬랙은 3초 안에 200을 못 받으면
같은 이벤트를 재시도한다. 그런데 모델이 툴을 두세 번 돌려 답을 만드는 데는 5~20초가 걸린다.
큐가 없으면 같은 답이 세 번 달린다. SQS가 그 경계다.

배포되는 바이너리는 하나이고, 들어온 이벤트 모양을 보고 자기가 gateway인지 worker인지 고른다.

## 1단계 — 키워드 검색 (완료)

GitHub API로 `memories`를 통째로 읽어 60초 캐시에 얹고, 질문에서 뽑은 키워드로
제목·별칭·태그·본문을 점수 매겨 매칭한다. 모델은 개입하지 않는다.

지금도 죽지 않았다. **자연어 브레인이 실패하면 여기로 떨어진다.**

---

## 2단계 — 자연어 브레인 (완료)

모델에게 툴 네 개를 쥐여주고 루프를 돌린다. 모델이 "목록 좀 보여줘" → "이 노트 읽어줘" →
"이제 답을 쓸게" 순으로 스스로 진행한다.

`@봇 요즘 뭐 배웠지?` 하나로 검증했다. 답이 카테고리별로 묶이고 `status: growing`까지
읽혀 나왔는데, 둘 다 키워드 검색으로는 나올 수 없는 정보다. 목록을 훑고 본문을 열어
프론트매터를 읽었다는 뜻이다.

### 조용해지지 않는 3중 안전망

| 상황 | 동작 |
|---|---|
| API 키 없음 | 1차 키워드 검색으로 답함 |
| Anthropic API 실패·과부하 | 키워드 검색으로 폴백 |
| SQS 전송 실패 | gateway가 그 자리에서 답함 (느리지만 답은 감) |

봇이 침묵하는 것이 가장 나쁜 실패다. 어떤 경로가 죽어도 답은 나가게 만들었다.

### 뚜껑

최대 5턴, 응답 1024토큰, 노트 본문 6000자, worker 동시 실행 2개.
질문 하나가 폭주해서 요금이 되는 경로를 막아둔 것.

## 3단계 — 쓰기 (다음)

붙여넣은 글을 [노트 작성 스타일](../docs/note-style.md)대로 정리해 위키에 올린다.

**읽기와 쓰기는 성질이 다르다.** 읽기는 틀려도 답이 이상할 뿐이지만, 쓰기는 위키를
오염시키고 되돌리려면 사람 손이 든다. 그래서 단계를 네 조각으로 쪼갠다.

### 3a. 쓰기 없이 정리만 (위험 0)

읽기 허용 경로에 `docs/`와 루트 `CONVENTIONS.md`를 더하고, 응답 토큰 상한을 올리고,
"정리 요청이면 규칙을 읽고 경로·프론트매터까지 만들어 답하라"를 프롬프트에 넣는다.

그러면 슬랙에 글을 붙이면 **"`topics/cs/grpc.md`에, 프론트매터는 이것, 이 섹션 추가"**까지
텍스트로 답한다. 파일 만들고 커밋하는 것만 손으로. 쓰기 권한이 전혀 없는데 가치의 대부분을 얻는다.

지금 이걸 막고 있는 건 두 줄이다 — 읽기 화이트리스트가 `topics/ daily/ personal/ projects/`
넷뿐이라 `docs/note-style.md`를 못 읽고, `maxTokens`가 1024라 노트 전문이 잘린다.

### 3b. PR로 올리기

`propose_note` 툴 하나를 더한다. 브랜치를 따고 파일을 만들고 PR을 연다.

```
git/ref/heads/main  →  base sha
git/refs            →  bot/note-<slug> 브랜치
contents/<path>     →  파일 생성
pulls               →  PR 열기
```

**PR 자체가 승인 게이트다.** 봇은 열기만 하고 머지는 못 한다. 사람이 머지하지 않으면
`main`은 그대로다. 되돌리기가 "PR 닫기"로 끝나는 게 이 설계의 값어치다.

새 파일만 만들 수 있고 기존 파일 덮어쓰기는 코드에서 막는다. 쓰기 토큰은 읽기 토큰과
**분리된 환경변수**로 두고, 읽기 클라이언트는 그 값을 볼 수 없게 타입을 나눈다.

### 3c. 슬랙에서 승인

👍 리액션으로 머지. `reactions:read` 스코프와 `reaction_added` 이벤트 구독이 추가로 필요하다.
편의 기능이지 안전장치가 아니다 — 안전장치는 이미 3b의 PR이다.

### 3d. 기존 노트 수정

`propose_edit`. 새로 만드는 것보다 어렵다. 기존 본문을 읽고 어디를 어떻게 바꿀지 정해야 하고,
그 사이 파일이 바뀌었을 가능성도 다뤄야 한다. 마지막에 한다.

## 설계 원칙 (안 바꾼다)

1. **모델은 GitHub를 직접 만지지 않는다.** 정해진 툴만 부르고, 각 툴은 자기 인자를 코드에서 검증한다.
2. **권한 검사는 프롬프트가 아니라 코드로.** 읽기 경로는 `IsNotePath()` 화이트리스트가 막는다.
   프롬프트로 막은 것은 뚫린다고 가정한다.
3. **읽기 툴과 쓰기 툴은 분리한다.** 토큰도, 타입도.
4. **모든 쓰기는 미리보기 + 승인을 거친다.** 무조건 덮어쓰기 금지.
5. **툴은 구조화된 JSON을 돌려주고, 말은 렌더 레이어가 만든다.**
6. **시크릿은 환경변수에만.** 코드·위키·대화 어디에도 두지 않는다.

## 결정 기록

| 결정 | 대안 | 왜 |
|---|---|---|
| 비동기를 SQS로 | 즉시 응답, Lambda 비동기 호출 | 슬랙 3초 제한 대 5~20초 응답. 큐가 없으면 중복 답변 |
| 동시성 상한을 `maximumConcurrency`로 | `reservedConcurrency` | 후자는 계정 동시성 풀에서 떼어가는데, 신규 계정 총 한도가 10이라 배포가 거절됨 |
| 모델은 Haiku | Sonnet | 이 용도엔 충분하고 5배 싸다. `LLM_MODEL`로 언제든 교체 |
| 바이너리 하나로 두 역할 | 함수별 개별 패키징 | 배포·버전이 단순. 이벤트 모양으로 역할 분기 |
| SigV4 직접 구현 | AWS SDK 의존 | 바이너리 크기, 그리고 서명이 어떻게 도는지 배우려고. AWS 공식 테스트 벡터로 검증 |
| 읽기 화이트리스트를 코드에 | 프롬프트로 지시 | 프롬프트 인젝션에 뚫린다 |

## 비용

Haiku 4.5 기준 ($1 / $5 per MTok).

| 종류 | 입력 | 출력 | 건당 |
|---|---|---|---|
| 평상시 질문 | 3~8k | 200~400 | 약 $0.01 |
| 노트 정리 (3단계) | 25~35k | 3~4k | 약 $0.05 |

노트 정리가 비싼 건 붙여넣은 글이 툴 루프마다 재전송되고 출력이 노트 전문이라서다.
그래도 100건 정리에 $5 수준. AWS 쪽은 Lambda·SQS 모두 프리티어 안에서 논다.

**절약 지점:** 스타일을 보이려고 기존 노트 전문을 읽히면 건당 3천 토큰이 그냥 나간다.
[노트 작성 스타일](../docs/note-style.md)을 대신 읽히면 그 비용이 사라진다 —
그 문서를 판정 가능한 형태로 유지해야 하는 실질적인 이유다.
